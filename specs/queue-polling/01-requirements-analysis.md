# 需求分析说明书: AI模型排队轮询机制

**功能分支**: `queue-polling`
**创建日期**: 2026-04-29
**状态**: 草稿
**输入**: 在codegenie-cli中集成AI中控排队机制，当模型请求返回排队错误时轮询等待，用户取消时调用退出排队接口

---

## 1. 简介

### 1.1 目的

本文档描述codegenie-cli的AI模型排队轮询机制需求分析。当后端AI模型服务返回排队错误（406/WaitingInLine）时，CLI需要：
1. 识别排队状态并在终端界面显示排队提示
2. 按固定步长延迟轮询重试直到排上
3. 支持用户主动取消排队并调用退出排队接口

### 1.2 范围

**包含**:
- 406排队错误识别（`error.code === "406" && error.type === "WaitingInLine"`）
- 固定步长延迟轮询（2→4→6→8→10→10→10秒）
- 排队位置动态更新（从每次406响应中提取最新位置）
- CLI终端对话区域排队状态显示（ℹ图标 + 排队提示文案）
- 用户Ctrl+C取消排队
- 退出排队API调用（`/sse/codeGenie/exitSessionQueue`）

**不包含**:
- 其他错误码的处理（保持现有retry逻辑）
- 排队优先级调整或跳过排队
- 多会话排队状态汇总

### 1.3 假设和约束

| 类型 | 描述 |
|------|------|
| 假设 | 退出排队API与模型API共用相同的baseURL |
| 假设 | sessionId已通过`x-codegenie-session`或`x-session-affinity`header发送 |
| 假设 | modelId可从当前会话的user message或agent配置中获取 |
| 约束 | 排队轮询延迟为固定步长（2、4、6、8、10...），非指数退避 |
| 约束 | 最大延迟10秒，超过后保持10秒间隔 |
| 约束 | 排队提示显示在聊天消息区域，非toast或status bar |
| 约束 | Header使用精确的`sessionId`而非`x-codegenie-session` |
| 约束 | 使用现有Ctrl+C中断机制，不新增用户入口。排队退出逻辑集成到processor.ts已有的Effect.onInterrupt中 |

### 1.4 术语与缩写

| 术语/缩写 | 全称 | 说明 |
|-----------|------|------|
| WaitingInLine | 排队等待 | AI后端返回的排队状态错误类型 |
| Queue Error | 排队错误 | 406状态码 + WaitingInLine类型的组合 |
| Exit Queue API | 退出排队接口 | 用户取消排队时调用的API |
| Session ID | 会话标识 | 当前对话会话的唯一标识符 |
| Model ID | 模型标识 | 当前使用的AI模型标识符 |

## 2. 系统上下文

### 2.1 系统定位

排队轮询机制位于LLM请求流程的错误处理层，是现有retry机制的扩展分支。当检测到排队错误时，触发排队专用重试策略而非标准重试。

## 3. 需求分析概述

### 3.1 需求来源

- AI后端在高负载时返回排队错误，用户需要等待或取消
- 当前CLI没有专门的排队处理机制，用户看不到排队状态
- 用户取消排队后需要通知后端释放排队资源

### 3.2 需求目标

1. 自动检测排队错误并进入排队轮询状态
2. 在CLI终端显示排队位置，让用户了解等待进度
3. 支持用户主动取消排队，释放后端资源
4. 排队成功后自动恢复请求处理

### 3.3 关键利益相关者

| 角色 | 职责 | 关注点 |
|------|------|--------|
| CLI用户 | 使用AI辅助开发 | 排队状态是否可见、取消是否便捷 |
| AI后端 | 提供模型服务 | 排队资源是否正确释放 |
| 迁移工程师 | 实现排队机制 | 与现有retry系统的兼容性 |

## 4. 需求场景分析

### 4.1 用户操作场景

**场景 US-001: 自动排队等待** (优先级: P1)

| 项目 | 描述 |
|------|------|
| 场景描述 | 用户发送请求，模型返回排队错误，CLI自动进入排队轮询 |
| 前置条件 | 已登录CodeGenie，选择模型并发起对话 |
| 操作步骤 | 1. 用户输入请求<br>2. 模型返回406排队错误<br>3. CLI显示排队提示（ℹ + 排队位置）<br>4. CLI按固定间隔轮询<br>5. 排上后排队提示消失，聊天区域正常响应 |
| 预期结果 | 排队状态可见，排上后排队提示移除，恢复正常聊天 |
| 关键规则 | 延迟序列：2→4→6→8→10→10→10秒；排队成功后QueuePart移除 |

**场景 US-002: 用户取消排队** (优先级: P1)

| 项目 | 描述 |
|------|------|
| 场景描述 | 用户在排队等待期间通过现有Ctrl+C机制取消（无新增入口） |
| 前置条件 | 当前处于排队轮询状态 |
| 操作步骤 | 1. 用户按下Ctrl+C（使用现有中断入口）<br>2. processor.ts的Effect.onInterrupt触发<br>3. 检测到排队状态后调用退出排队API<br>4. 排队提示消失，会话终止 |
| 预期结果 | 后端排队资源释放，排队提示移除，会话结束 |
| 关键规则 | Header: sessionId, Body: modelId；复用现有中断入口；取消后QueuePart移除 |

**场景 US-003: 排队位置更新** (优先级: P2)

| 项目 | 描述 |
|------|------|
| 场景描述 | 排队过程中位置变化，CLI更新显示 |
| 前置条件 | 处于排队轮询状态 |
| 操作步骤 | 1. 轮询请求返回新的406响应<br>2. 解析新的排队位置<br>3. 更新终端显示 |
| 预期结果 | 排队位置实时更新 |
| 关键规则 | 每次轮询都解析位置 |

### 6.1 性能要求

| 指标 | 要求 | 说明 |
|------|------|------|
| 延迟精度 | ±500ms | 轮询延迟控制在合理范围 |

### 6.2 兼容性

| 兼容类型 | 要求 | 说明 |

| Retry兼容 | 不影响现有retry逻辑 | 排队是独立的retry分支 |

| Effect-TS兼容 | 遵循现有Effect模式 | 使用Effect.gen/fn/retry |

## 附录

### A. API规格

**退出排队API**:

```
POST /sse/codeGenie/exitSessionQueue

Headers:
  sessionId: <session-id-string>

Body:
  { "modelId": "<model-id-string>" }

Response:
  { "code": "200", "message": "success", "data": true }
```

**排队错误响应格式**:

```json
{
  "error": {
    "code": "406",
    "type": "WaitingInLine",
    "message": "当前模型访问量较高，您目前排在第${index}位，请耐心等待。",
    "param": null
  }
}
```
