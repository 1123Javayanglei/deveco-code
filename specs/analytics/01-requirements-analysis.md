# 需求分析说明书: 用户行为打点 (Analytics)

**功能分支**: `005-analytics`  
**创建日期**: 2026-04-27  
**状态**: 已实现  
**输入**: 用户描述: "在 CodeGenie CLI 中集成用户行为打点系统，采集用户与 AI 的交互数据，上报至华为云端"

---

## 1. 简介

### 1.1 目的

本文档描述 CodeGenie CLI 用户行为打点系统的需求分析，明确打点数据的采集范围、上报机制、用户标识策略等核心需求。

### 1.2 范围

**包含**：
- 用户与 AI 交互数据的采集（query、answer、token、工具调用等）
- 打点数据的持久化、批量上报、失败重试
- 用户标识（uid/userid）的生成与持久化
- 登录状态校验与条件采集

**不包含**：
- 服务端数据接收与存储
- 数据分析与可视化
- 用户行为归因与推荐

### 1.3 假设和约束

| 类型 | 描述 |
|------|------|
| 假设 | 用户已登录华为账号，打点仅在登录状态下触发 |
| 假设 | 上报端点可用且网络可达 |
| 约束 | 打点数据按单次请求（messageID）隔离，非整个会话 |
| 约束 | 上报格式必须符合 HuaweiTracePayload 规范 |

### 1.4 术语与缩写

| 术语/缩写 | 全称 | 说明 |
|-----------|------|------|
| uid | Unique Device ID | 设备级匿名标识，UUID 格式 |
| userid | User ID | 华为账号登录后的真实用户 ID |
| messageID | Message ID | 用户单次请求的唯一标识 |
| sessionID | Session ID | 对话会话标识 |
| JWT | JSON Web Token | 华为账号认证令牌 |

## 2. 系统上下文

### 2.1 系统定位

打点系统作为 CodeGenie CLI 的插件模块，通过 OpenCode 插件 Hook 机制采集用户交互数据，经持久化和批量处理后上报至华为云端。

### 2.2 系统边界

```
┌─────────────────────────────────────────────┐
│              CodeGenie CLI                    │
│                                               │
│  ┌──────────┐    ┌──────────┐    ┌────────┐ │
│  │ Plugin   │───▶│ Collector│───▶│Uploader│ │
│  │ Hooks    │    │          │    │        │ │
│  └──────────┘    └──────────┘    └───┬────┘ │
│                                       │      │
│  ┌──────────┐    ┌──────────┐        │      │
│  │ Storage  │    │ Codegenie│        │      │
│  │ (Disk)   │    │ Auth     │        │      │
│  └──────────┘    └──────────┘        │      │
└──────────────────────────────────────┼──────┘
                                       │
                              ┌────────▼────────┐
                              │  华为云端 API    │
                              │  /cli/trace/     │
                              │  upload          │
                              └─────────────────┘
```

### 2.3 系统架构图

打点系统由 4 个核心模块组成：
- **AnalyticsPlugin**: 插件入口，注册 Hook，触发数据采集
- **SessionCollector**: 会话数据收集器，维护 SessionContext
- **AnalyticsUploader**: 事件上传器，队列管理、批量上报、重试
- **Storage**: 持久化存储，uid/userid/pendingEvents

## 3. 需求分析概述

### 3.1 需求来源

- 产品需要了解用户使用 CodeGenie CLI 的行为模式
- 需要统计各 Agent 类型的使用频率
- 需要监控 Token 消耗和工具调用情况
- 需要衡量请求成功率和响应时效

### 3.2 需求目标

- 采集用户每次请求的完整交互数据
- 可靠上报至华为云端，不丢失数据
- 准确标识用户身份和设备

### 3.3 关键利益相关者

| 角色 | 职责 | 关注点 |
|------|------|--------|
| 产品经理 | 分析用户行为 | 数据完整性和准确性 |
| 开发工程师 | 实现打点功能 | 性能影响、代码侵入性 |
| 运维工程师 | 监控上报状态 | 上报成功率、重试机制 |

## 4. 需求场景分析

### 4.1 业务场景

#### 4.1.1 业务流程图

```
用户发消息 → chat.message Hook → startSession(创建context)
    ↓
模型多轮交互 → event Hook → 累加数据(tokens/tools/answer)
    ↓
session.idle → buildEvent(打包) → upload(入队) → flush(上报)
```

#### 4.1.2 业务规则

| 规则编号 | 规则名称 | 规则描述 | 优先级 |
|----------|----------|----------|--------|
| BR-001 | 登录校验 | 仅用户已登录华为账号时才采集和上报 | 高 |
| BR-002 | Provider 校验 | 仅使用 codegenie provider 时才采集 | 高 |
| BR-003 | 数据隔离 | 打点数据按 messageID 隔离，非整个 session | 高 |
| BR-004 | 持久化优先 | 事件先持久化到磁盘，防止进程异常丢失 | 中 |

### 4.2 用户操作场景与关键路径

#### 4.2.1 用户角色定义

| 角色ID | 角色名称 | 角色描述 | 权限范围 |
|--------|----------|----------|----------|
| UR-001 | 已登录用户 | 已登录华为账号的 CodeGenie 用户 | 完整打点采集 |
| UR-002 | 未登录用户 | 未登录的 CodeGenie 用户 | 不采集 |

#### 4.2.2 用户操作场景

**场景 US-001: 已登录用户正常使用** (优先级: P1)

| 项目 | 描述 |
|------|------|
| 场景描述 | 已登录用户使用 build agent 发起请求，模型多轮交互后完成 |
| 前置条件 | 用户已登录华为账号，使用 codegenie provider |
| 操作步骤 | 1. 用户输入问题<br>2. 模型调用工具并回答<br>3. 会话进入 idle 状态 |
| 预期结果 | 完整打点数据被采集并上报，包含 query/answer/tokens/tools/agent 等 |
| 异常处理 | 上报失败时持久化到磁盘，等待下次重试 |

**场景 US-002: 未登录用户使用** (优先级: P2)

| 项目 | 描述 |
|------|------|
| 场景描述 | 未登录用户使用 CodeGenie |
| 前置条件 | 用户未登录华为账号 |
| 操作步骤 | 1. 用户输入问题<br>2. 模型回答 |
| 预期结果 | 不采集任何打点数据 |
| 异常处理 | 无 |

**场景 US-003: 进程异常退出** (优先级: P2)

| 项目 | 描述 |
|------|------|
| 场景描述 | 用户使用过程中进程被 SIGINT/SIGTERM 终止 |
| 前置条件 | 有未上报的打点事件 |
| 操作步骤 | 1. 进程收到信号<br>2. 执行 shutdown flush |
| 预期结果 | 未上报事件持久化到磁盘，下次启动时恢复 |

### 4.3 研发与维护阶段场景

#### 4.3.1 开发阶段场景

| 场景 | 描述 | 注意事项 |

| 日志调试 | 通过 analytics.log 查看打点数据详情 | 日志仅记录关键字段，query/answer 截取前 200 字符 |

#### 4.3.2 测试阶段场景

| 重试验证 | 模拟网络失败，验证重试机制 | 最多重试 5 次后丢弃 |

#### 4.3.3 运维阶段场景

| 场景 | 描述 | 运维要求 |
|------|------|----------|
| Token 刷新 | 上报时 Token 过期自动刷新 | 刷新失败则跳过上报 |

## 5. 功能性需求分析

### 5.1 功能需求列表

| 需求编号 | 需求名称 | 需求描述 | 优先级 | 来源 |
|----------|----------|----------|--------|------|
| FR-001 | 打点数据采集 | 采集用户每次请求的完整交互数据 | P1 | 产品需求 |
| FR-002 | 打点条件校验 | 仅登录且使用 codegenie provider 时采集 | P1 | 产品需求 |
| FR-003 | 打点数据上报 | 批量上报至华为云端，支持重试 | P1 | 产品需求 |
| FR-004 | 用户标识 | uid 设备标识 + userid 华为账号标识 | P1 | 产品需求 |
| FR-005 | 请求标识 | sessionID 会话标识 + messageID 请求标识 | P1 | 产品需求 |
| FR-006 | Agent 标识 | 记录当前使用的 Agent 类型 | P1 | 产品需求 |
| FR-007 | 进程生命周期 | 启动恢复 pending 事件，退出执行最终 flush | P2 | 可靠性需求 |
| FR-008 | Token 自动刷新 | 上报时 Token 过期自动刷新 | P2 | 可靠性需求 |

### 5.2 功能需求详细说明

#### FR-001: 打点数据采集

| 项目 | 描述 |
|------|------|
| 需求描述 | 采集用户每次请求（messageID）的完整交互数据，包括 query、answer、inputTokenCount、outputTokenCount、toolExecutions、modifiedFileList、operations、isSuccess、totalElapsed、firstResultElapsed、os_name、os_version |
| 验收标准 | 1. 每次用户请求产生一条完整的 AnalyticsEvent<br>2. 所有字段均有有效值<br>3. 数据按 messageID 隔离 |
| 关联场景 | US-001 |
| 依赖需求 | FR-002, FR-004, FR-005, FR-006 |

#### FR-002: 打点条件校验

| 项目 | 描述 |
|------|------|
| 需求描述 | 仅在用户已登录华为账号且使用 codegenie provider 时采集打点数据 |
| 验收标准 | 1. 未登录时不采集<br>2. 非 codegenie provider 时不采集 |
| 关联场景 | US-001, US-002 |
| 依赖需求 | 无 |

#### FR-003: 打点数据上报

| 项目 | 描述 |
|------|------|
| 需求描述 | 将 AnalyticsEvent 转换为 HuaweiTracePayload 格式，批量上报至华为云端 |
| 验收标准 | 1. 上报格式符合 HuaweiTracePayload<br>2. 支持批量上报（batchSize=10）<br>3. 支持失败重试（maxRetries=5）<br>4. 事件先持久化到磁盘 |
| 关联场景 | US-001 |
| 依赖需求 | FR-001 |

#### FR-004: 用户标识

| 项目 | 描述 |
|------|------|
| 需求描述 | uid 为设备级匿名标识（UUID），userid 为华为账号真实用户 ID。userid 在登录时从 JWT 解析并持久化到磁盘 |
| 验收标准 | 1. uid 首次生成后持久化复用<br>2. userid 从 JWT token 解析<br>3. userid 持久化到磁盘，进程重启后可读取 |
| 关联场景 | US-001 |
| 依赖需求 | FR-002 |

#### FR-005: 请求标识

| 项目 | 描述 |
|------|------|
| 需求描述 | sessionID 标识整个对话，messageID 标识用户单次请求 |
| 验收标准 | 1. sessionID 从 chat.message hook 的 input 获取<br>2. messageID 从 chat.message hook 的 input 获取 |
| 关联场景 | US-001 |
| 依赖需求 | 无 |

#### FR-006: Agent 标识

| 项目 | 描述 |
|------|------|
| 需求描述 | 记录当前使用的 Agent 类型（build/plan/debug 等） |
| 验收标准 | 1. agentName 从 chat.message hook 的 input.agent 获取<br>2. 未指定时默认 "unknown" |
| 关联场景 | US-001 |
| 依赖需求 | 无 |

#### FR-007: 进程生命周期

| 项目 | 描述 |
|------|------|
| 需求描述 | 进程启动时恢复磁盘上未上报的 pending 事件，退出时执行最终 flush |
| 验收标准 | 1. 启动时恢复 pending 事件到队列<br>2. SIGINT/SIGTERM 时执行 flush |
| 关联场景 | US-003 |
| 依赖需求 | FR-003 |

#### FR-008: Token 自动刷新

| 项目 | 描述 |
|------|------|
| 需求描述 | 上报时检测 Token 过期，自动刷新后再上报 |
| 验收标准 | 1. Token 过期时调用 refreshToken<br>2. 刷新成功后使用新 Token 上报<br>3. 刷新失败则跳过上报 |
| 关联场景 | US-001 |
| 依赖需求 | FR-003 |

### 5.3 功能依赖关系

```
FR-002(条件校验) ──→ FR-001(数据采集) ──→ FR-003(数据上报)
FR-004(用户标识) ──→ FR-001(数据采集)
FR-005(请求标识) ──→ FR-001(数据采集)
FR-006(Agent标识) ──→ FR-001(数据采集)
FR-003(数据上报) ──→ FR-007(生命周期)
FR-003(数据上报) ──→ FR-008(Token刷新)
```

## 6. 非功能性需求分析

### 6.1 系统可靠性

| 指标 | 要求 | 说明 |
|------|------|------|
| 数据不丢失 | 事件先持久化到磁盘 | 防止进程异常退出丢失 |
| 上报重试 | 最多 5 次 | 超过后丢弃 |
| 定时刷新 | 每 30 秒 | 确保事件及时上报 |

### 6.2 安全隐私

#### 6.2.1 安全需求

| 安全类型 | 需求描述 | 安全等级 |
|----------|----------|----------|
| 身份认证 | 上报请求携带华为账号 Token | 高 |
| 数据传输 | 使用 HTTPS 加密传输 | 高 |

#### 6.2.2 隐私需求

| 隐私类型 | 需求描述 | 合规要求 |
|----------|----------|----------|
| 数据收集 | 仅采集使用行为数据，不采集源码内容 | query/answer 截取前 200 字符记入日志 |
| 数据存储 | 本地仅存储 pending 事件，上报后清除 | 磁盘持久化 |

### 6.3 可测试性

| 测试类型 | 测试要求 | 覆盖率目标 |
|----------|----------|------------|
| 日志验证 | 通过 analytics.log 验证打点字段完整性 | 关键字段 100% |
| 上报验证 | 检查上报请求格式和内容 | HuaweiTracePayload 格式正确 |

## 7. 系统影响分析

### 7.1 功能影响列表
